# Coverage: popular data targets

Probed 2026-11-07 from Linux-7.0.0-1019-azure-x86_64-with-glibc2.43, once per target, 2 s apart, with the honest user agent.

One request per site on one machine is a **snapshot**, not a verdict about the site: reachability depends on the IP, the time of day and what the site was doing that minute. Rows marked tier 3 were walled for this machine; a proxy or a browser may still get through, and this table is not a promise that it will.

Of 40 targets: **16 returned rows**, 2 returned a couple, 10 returned a JavaScript shell, 2 returned a repeated block that is not the data, 10 were walled.

| verdict | means |
|---|---|
| rows | 5 or more item blocks found in the HTML that came back |
| thin | 1 to 4: a real page, not a listing, or a listing mostly drawn by script |
| shell | HTTP 200 and zero items: the page exists, the data is drawn later by JavaScript |
| noise | a repeated block was found, but it is tracking or settings JSON, not records |
| no-price | a marketplace page returned repeated blocks with no price: a carousel or nav, not the listing |
| walled | both tier 1 and tier 2 were refused: status code or challenge page |

## Reading a row

- **tier 1**: plain HTTP was enough. **tier 2**: only TLS impersonation got real HTML. **tier 3**: both were walled; the note says whether it was a status code or a challenge page.
- A `blocked` note with HTTP 200 usually means a JavaScript shell: the server sent a page, and the list is fetched later by the browser. The fix for those is tier 3 or that site's JSON API, not a better selector.
- Sites that answer only behind a login are not attempted by tiers 1-3 at all. The tool reports `blocked` and stops; it does not have your password.
